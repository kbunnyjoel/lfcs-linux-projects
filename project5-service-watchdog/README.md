# Project 5: Service Watchdog

## Overview
The Service Watchdog is a monitoring tool designed to keep track of the health of specified services. It performs health checks on services and can optionally restart them if they are found to be unhealthy. The tool outputs its status in JSON format, making it easy to integrate with other tools or dashboards. It is designed to be run periodically via cron jobs or inside Docker containers for continuous monitoring.

## Quickstart
Get started quickly with the following commands:

```bash
# Build the Docker image (if using Docker)
make build

# Run the test suite
make test

# Run the watchdog with your environment file
./watch.sh --env env/dev

# Or continuously monitor services in the background
./watch.sh --env env/prod &
```

The `make build` and `make test` commands use Docker if available. You can also run `./watch.sh` directly for local monitoring. Make sure your `env/dev` or `env/prod` configuration files exist and are set up as described below.

## Usage
The primary interface to the Service Watchdog is the `watch.sh` script. It supports the following commands and options:

- `watch.sh check`  
  Runs health checks on specified services.

- Options:  
  `--env <env_file>`  
  Specify the environment file defining the services to monitor (e.g., `env/dev` or `env/prod`).  

  `--services <service1,service2,...>`  
  Comma-separated list of services to check.  

  `--json`  
  Output the health check results in JSON format to stdout.  

  `--health-cmd <command>`  
  Custom command to check the health of a service.  

  `--start-cmd <command>`  
  Custom command to start a service if it is unhealthy. This option can also be used as `--restart-cmd`.  

  `--once`  
  Run the health check only once and then exit (no continuous monitoring).  

  `--max-retries <N>`  
  Maximum number of retry attempts for restarting a service.  

  `--retry-interval <SEC>`  
  Initial retry interval in seconds between attempts.  

  `--retry-max-interval <SEC>`  
  Maximum retry interval in seconds for backoff.  

  `--backoff <linear|exp>`  
  Backoff strategy to use between retries: linear or exponential.  

  `--jitter <0..1>`  
  Jitter factor to add randomness to retry intervals to avoid thundering herd.

Environment variables can now be used as defaults for these options (Option 2). For example, setting `WATCH_MAX_RETRIES` or `WATCH_RETRY_INTERVAL` in your environment file will provide default values for the corresponding options.

**Note:** Command-line flags take precedence over environment variables, which in turn take precedence over built-in defaults.

In addition to `watch.sh`, the `notify.sh` script is provided to send notifications or log messages. It supports the following options:

- `notify.sh`  
  Sends notifications or logs messages based on the provided parameters.

- Options:  
  `--env <env_file>`  
  Specify the environment file containing notification configuration (e.g., `env/dev` or `env/prod`).  

  `--to <email>`  
  Recipient email address for notifications.  

  `--from <email>`  
  Sender email address.  

  `--subject <subject>`  
  Subject line for the notification email.  

  `--body <message>`  
  Body content of the notification email or log message.  

  `--level <level>`  
  Severity level of the notification (e.g., info, warning, error).  

  `--json`  
  Output notification data in JSON format to stdout.

### Exit Codes
- `0` - All services are healthy.  
- `1` - One or more services are degraded or unhealthy.  
- `2` - Usage error (invalid arguments or missing parameters).

## Notifications
The `notify.sh` script prefers to send emails using `msmtp` or `sendmail` if available, but will fall back to writing notifications to a log file if those are not configured.

To send a test email or log message using the `notify.sh` script, run:

```bash
./notify.sh --env env/dev --to user@example.com --from watchdog@example.com --subject "Test Notification" --body "This is a test notification from Service Watchdog." --level info
```

Alternatively, to output a notification in JSON format to stdout:

```bash
./notify.sh --env env/prod --json
```

## Environment
The `env/` directory contains environment files such as `dev` and `prod` which define the services to monitor and their related configuration. These files specify which services the watchdog should watch and can be customized per deployment environment.

Example `dev.env`:

```
# Services to monitor
SERVICES=nginx,mysql,redis

# Notification settings
WATCH_EMAIL=dev-team@example.com
WATCH_FROM_EMAIL=watchdog-dev@example.com

# Retry and backoff settings
WATCH_MAX_RETRIES=3
WATCH_RETRY_INTERVAL=5
WATCH_RETRY_MAX_INTERVAL=60
WATCH_BACKOFF=linear
WATCH_JITTER=0.1
```

Example `prod.env`:

```
# Services to monitor
SERVICES=nginx,mysql,redis,memcached

# Notification settings
WATCH_EMAIL=ops-team@example.com
WATCH_FROM_EMAIL=watchdog-prod@example.com

# Retry and backoff settings
WATCH_MAX_RETRIES=5
WATCH_RETRY_INTERVAL=10
WATCH_RETRY_MAX_INTERVAL=120
WATCH_BACKOFF=exp
WATCH_JITTER=0.2
```

## Troubleshooting
Here are some common issues and solutions:

- **Missing `env/dev` or `env/prod` files:**  
  Make sure the required environment file exists in the `env/` directory. Copy and adapt the provided examples if needed.

- **Email notifications not working (msmtp/sendmail):**  
  Ensure `msmtp` or `sendmail` is installed and configured on your system. Check your environment file for correct email addresses and SMTP settings.

- **Permission errors on logs or outputs:**  
  The scripts write to `logs/` and `outputs/`. If you see permission denied errors, ensure your user has write access to these directories:
  ```bash
  chmod -R u+rw logs/ outputs/
  ```

- **Docker build or test failures:**  
  Check that Docker is running and you have permission to use it. Review the output for missing dependencies or configuration files.
